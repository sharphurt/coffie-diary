### Быстрый учёт чашки — 14.11.2026

Реализован раздел 11.3: одно нажатие на карточке, блокировка на время запроса, сообщение с отменой и оценкой существующей чашки. При ошибке результат помечается неподтверждённым; повтор отправляет прежние clientEventId и объём. Новое намеренное действие после завершения получает новый UUID. Ошибка обновления счётчиков после успешного POST не выдаётся за ошибку сохранения.

`quick cup: lost response retries once, undo and rating notification` в `frontend/e2e/diary.spec.ts` выполняется на desktop и mobile с реальным API: первый POST доходит до БД, его ответ обрывается, повтор возвращает тот же event; count не удваивается. Проверены отмена, новый ID следующего действия, закрытие анкеты без потери чашки и оценка без нового event. Итого 6 E2E PASS, 9 frontend PASS, 8 backend PASS; production build PASS. Полный выбор профилей и редактирование events ещё не реализованы.

### Пробелы тестового покрытия

- **Этап 1.** Изоляция профилей и сохранность тома фото подтверждены. Сборка штатного production-образа в этом прогоне не подтверждена.
- **Этап 2.** Конкурентная привязка одной оценки к двум чашкам проверена на PostgreSQL: ответы 200/409, ровно одна связь, проигравшая запись без изменений. Привязка чужой оценки проверена в обе стороны под отдельными сессиями: 404 и неизменные записи. Остаётся фильтр источника после связи с каталогом. Удаление и восстановление лота и пачки со связанной историей проверены E2E.
- **Оба этапа.** Текущие тесты проверяют отдельные конфликты версий, повторы запросов и границы суток. AC-40 подтверждён интеграционными проверками двух владельцев и параллельных правок. Исчерпывающая проверка границ всех входных полей каждой операции остаётся за пределами этого прогона. Запуск E2E покрывает desktop/mobile Chromium. Сенсорные шкалы и фото на всех ширинах AC-41 ещё не подтверждены.

### Контейнерная проверка этапа 1

На WSL Docker 29.1.3 / Compose 2.40.3 запущен отдельный проект с томами из docker-compose.yml. Для теста использованы temurin 21-jre, PostgreSQL 18 Alpine с PGDATA=/var/lib/postgresql/data и собранный Maven JAR с production-фронтендом. Штатная сборка Dockerfile не вошла в этот прогон из-за загрузки образов. Через API созданы пачка и два фото. После compose up --force-recreate --wait ID обоих контейнеров изменились, именованные тома сохранились. Контрольные суммы четырёх файлов, обложка и порядок совпали.

Для повторения на отдельном тестовом Compose-проекте задайте E2E_BASE_URL и OWNER_PASSWORD, выполните node tools/check-compose-media.mjs seed <файл-состояния>, пересоздайте контейнеры без удаления томов и выполните node tools/check-compose-media.mjs verify <файл-состояния>.

tools/e2e.ps1 также подтвердил 10 E2E-сценариев desktop/mobile, сохранность фото при локальном перезапуске и изоляцию двух владельцев. Второй владелец видит только свои профили и получает 404 при попытке изменить, архивировать, назначить по умолчанию или использовать чужой профиль для чашки. Исходный профиль первого владельца остаётся неизменным.

Подтверждение сводок этапа 2: desktop/mobile E2E проверяет пачку с тремя оценками 1, 2, 3 и пачку с одной оценкой 4. Рейтинг лота равен 3 при двух оценённых пачках, третья пачка без оценок исключена. Итоговое впечатление 5 отображается отдельно от среднего по чашкам 2. Форму после завершения можно пропустить.

Проверки истории: desktop/mobile E2E проверяет поиск по обжарщику, сортировку до пагинации на 21 совпадении, фильтры статуса и оценки, сброс. Во «Выпито» один период и поисковый запрос дают 2 чашки / 450 мл, фильтр известных оставляет 1 / 250, фильтр неизвестных — 1 / 200. Фильтр источника нужен после появления подтверждённых связей с каталогом.

Сводные признаки (§12.5) — PASS на синтетических пороговых сценариях JUnit и интеграционном тесте PostgreSQL. Один аккаунт даёт максимум один согласованный голос на шкалу; повтор и анонимный текст не приближают к порогу. При n<3 статус UNKNOWN, ровно 2/3 при n=3 даёт CONSENSUS, а 2/4 даёт CONFLICTED. Живая проверка публичной карточки Tasty получила текст без стабильного ID автора. Консенсус реальных покупателей для этой выборки не подтверждён.

Дескрипторы производителя (§12.5) — PASS. Тесты адаптеров и живой импорт FOLK и Tasty Coffee проверяют нормализацию, исходный текст и ссылку на товар. Тест PostgreSQL подтверждает, что изменение дескрипторов создаёт новую ревизию, сохраняет предыдущий снимок и не добавляет наблюдений по отзывам.

Быстрая подборка FOLK — текущий режим выдачи. PostgreSQL проверяет сходство после высокой оценки, контраст после низкой, равный вес пачек, фильтры обжарки, бюджета и наличия, а также исключение Tasty Coffee. Тест интерфейса проверяет объяснение и переход к лотам. Прежние результаты по Tasty Coffee и признакам отзывов относятся к компонентам расширенной модели.
