# Техническое задание: личный кофейный дневник и рекомендации

Версия документа: 1.0 · Дата: 13 ноября 2026 года  
Рабочее название: «Мой кофе»  
Формат первой версии: адаптивное веб-приложение на русском языке.  
Назначение документа: самостоятельное задание агенту-разработчику. Реализовать продукт, описанный ниже, и предоставить исходный код, инструкции запуска и результаты проверки.

## 1. Цель и пользовательский контекст

Пользователь покупает преимущественно пачки зернового кофе по 250 г, пьёт одну пачку некоторое время и может оценивать несколько приготовлений из неё. Требуется сохранять историю покупок и впечатлений, находить понравившийся кофе и выбирать следующий лот у разных обжарщиков.

Исходное оборудование пользователя:

- кофемолка MHW-3BOMBER Race M1;
- портативная кофеварка-пуровер Kitfort КТ-7570;
- бумажный фильтр;
- помол непосредственно перед приготовлением.

Нельзя исходить из того, что пользователь распознаёт дескрипторы обжарщика. Главные данные персонализации — его собственные оценки, ощущения и история. Описания обжарщиков и отзывы покупателей являются внешними признаками, а не объективной истиной о вкусе пользователя.

Основной цикл: добавить пачку → отметить, что пьёт её сейчас → фиксировать выпитые чашки и при желании оставлять оценки → завершить пачку → посмотреть рекомендации → купить/добавить следующую пачку. Выпитый кофе неизвестного лота также учитывается без создания фиктивной пачки.

## 2. Обязательная область V1

Все требования с префиксом MUST обязательны, если прямо не указано иное. Численные значения по умолчанию в этом документе — проектные решения, а не результаты исследования предпочтений пользователя.

### 2.1. Что входит

| ID | Требование |
|---|---|
| MVP-01 | Ручное создание лота с обязательным названием и необязательным обжарщиком. |
| MVP-02 | Создание купленной пачки этого лота; масса по умолчанию 250 г, редактируется. |
| MVP-03 | Загрузка фотографии пачки с телефона или компьютера без OCR и распознавания. |
| MVP-04 | Состояния пачки: «Запас», «Пью сейчас», «Закончена». Несколько открытых пачек разрешены. |
| MVP-05 | Неограниченное число оценок приготовлений из каждой пачки. |
| MVP-06 | Общая оценка, шесть сенсорных шкал, желание повторить покупку, необязательный комментарий и параметры приготовления. |
| MVP-07 | История всех лотов, пачек, фотографий и оценок; поиск, фильтры, редактирование. |
| MVP-08 | Личный рейтинг попробованного кофе с количеством пачек и оценок. |
| MVP-09 | Получение каталога кофе с folk.shop и shop.tastycoffee.ru. |
| MVP-10 | Использование доступных описаний, дескрипторов и пригодных отзывов о конкретном продукте. |
| MVP-11 | Рекомендации новых и ранее попробованных продуктов с объяснениями, происхождением данных и уровнем уверенности. |
| MVP-12 | Привязка вручную введённого лота к позиции каталога с подтверждением пользователя. |
| MVP-13 | Вход владельца, резервное копирование, постоянное хранение данных и фотографий. |
| MVP-14 | Адаптивный интерфейс, ориентированный прежде всего на использование в браузере телефона. |
| MVP-15 | Учёт всех выпитых чашек: из выбранной пачки или неизвестного кофе, без обязательной оценки. |
| MVP-16 | Объём чашки в профиле оборудования; количество чашек и объём за день, неделю, месяц и произвольный период. |

### 2.2. Что не входит

- OCR, распознавание пачки, штрихкода, сорта или обжарщика по фотографии.
- Автозаполнение названия после загрузки изображения.
- Нативное Android/iOS-приложение и публикация в магазинах приложений.
- Работа без сети, фоновая синхронизация офлайн-изменений, push-уведомления.
- Социальная сеть, публичные профили, собственная база отзывов других пользователей.
- Интеграция с заказами магазинов, корзина, оплата и оформление покупки.
- Автоматический расчёт остатка зерна и списание граммов после оценки.
- Универсальная шкала помола в микронах, обязательная калибровка кофемолки.
- Автоматическая диагностика ошибок заваривания и подбор рецепта нейросетью.
- Поиск «вкусовых двойников» среди авторов отзывов, collaborative filtering.
- Подключение Torrefacto и других обжарщиков; архитектура должна позволять добавить их позже.
- Kafka, Kubernetes, микросервисы, векторная БД, отдельный ML-сервис.

## 3. Решения по умолчанию

Это явно принятые допущения для реализации без дополнительного согласования каждой детали.

1. V1 обслуживает одного владельца. В БД личные сущности всё равно имеют owner_id; публичной регистрации нет.
2. Часовой пояс профиля — Asia/Yekaterinburg. Моменты времени хранятся в UTC, календарные даты обжарки/покупки — как date без сдвига часового пояса.
3. Валюта V1 — RUB. Иные валюты отображать как есть, не сравнивать с рублёвым бюджетом без конвертации; конвертация вне V1.
4. «Активен» относится к купленной пачке, а не к глобальному товару в каталоге. Длительность активности не ограничивается автоматически.
5. При быстром добавлении пачка сразу попадает в «Пью сейчас»; пользователь может выбрать «Запас».
6. У одного лота могут быть несколько покупок. Повторная покупка создаёт новую пачку, не очищает старые оценки.
7. Все сенсорные поля необязательны. Обязательна только общая оценка чашки.
8. LLM не обязательна для запуска V1: приложение и базовые рекомендации работают без внешнего AI-ключа.
9. Приложение размещается самостоятельно, например на домашнем Debian-сервере. Локальный запуск через Docker Compose. Публичное развёртывание не является частью реализации без отдельного поручения.

## 4. Предлагаемый технический стек

Выбор адаптирован к опыту пользователя с Java/Spring/PostgreSQL. Это предписание для нового проекта; при наличии готового репозитория сначала проверить его ограничения.

| Часть | Решение |
|---|---|
| Backend | Java 21, Spring Boot, Spring MVC, Spring Security, Spring Data JPA |
| База | PostgreSQL, миграции Flyway |
| Frontend | React + TypeScript + Vite, адаптивный CSS, доступные HTML-компоненты |
| API | JSON REST, префикс /api/v1, OpenAPI |
| Файлы | Локальный постоянный volume; интерфейс FileStorage для будущего S3 |
| Импорт | HTTP-клиент + HTML/JSON-парсеры; Playwright только при необходимости публичного JS-каталога |
| Фоновые задачи | Планировщик Spring и блокировки задач в PostgreSQL |
| Развёртывание | Docker Compose: приложение/веб, PostgreSQL, при необходимости отдельный процесс worker из того же кода |
| Тестирование | JUnit, Testcontainers PostgreSQL, frontend component tests, Playwright E2E |

Перед началом реализации выбрать совместимые поддерживаемые версии библиотек и зафиксировать их в build-файлах, lockfile и README. Не использовать плавающий latest для production-образов. Не устанавливать конкретную устаревшую версию только ради совпадения с этим документом.

Backend — модульный монолит: identity, diary, media, catalog, ingestion, recommendations. Веб-клиент обращается только к API; бизнес-логика не должна существовать исключительно во frontend. Это позволит позже добавить мобильный клиент. Специальную мобильную авторизацию и SDK в V1 не реализовывать.

## 5. Термины и идентичность кофе

| Сущность | Значение |
|---|---|
| Личный лот (PersonalLot) | Запись пользователя о кофе с ручным названием; объединяет повторные покупки. |
| Пачка (CoffeeBag) | Конкретная покупка/упаковка: масса, даты, статус, фото, итоговое впечатление. |
| Оценка приготовления (Tasting) | Одна чашка/одно приготовление из конкретной пачки. |
| Выпитая чашка (ConsumptionEvent) | Самостоятельная запись о потреблении: время, объём напитка, необязательные пачка и оценка. |
| Товар источника (CatalogProduct) | Стабильная карточка магазина, идентифицированная источником и внешним ID/каноническим URL. |
| Ревизия каталога (CatalogRevision) | Неизменяемый снимок значимых характеристик товара и периода их наблюдения. |
| Предложение (Offer) | Фасовка, цена и доступность товара в конкретном снимке. |
| Внешнее наблюдение | Утверждение об ощущениях, полученное из описания или отзыва с происхождением и уверенностью. |

Нельзя объединять товары разных обжарщиков по одному названию страны, фермы или дескрипторам. Изменение цены не создаёт новый лот. Изменение заявленного урожая, обработки, состава или профиля обжарки создаёт новую ревизию. При неизвестной партии нельзя выдавать ревизию карточки за подтверждённую партию зерна.

PersonalLot может быть связан с CatalogProduct. CoffeeBag дополнительно фиксирует catalog_revision_id, если версия известна. Привязка старой пачки к текущей карточке без сведений о партии сохраняется как «версия неизвестна». Исторические оценки не перепривязываются автоматически к новой ревизии.

## 6. Пользовательские сценарии

### US-01. Добавить кофе вручную

1. Пользователь нажимает «Добавить кофе».
2. Вводит название, при желании обжарщика и фото.
3. Масса уже равна 250 г; статус — «Пью сейчас».
4. Дополнительные поля свёрнуты: дата покупки/обжарки, цена, заметка, ссылка на товар.
5. После сохранения видит карточку пачки и кнопку «Оценить чашку».

Название — единственное обязательное пользовательское поле этой формы. Сервер создаёт PersonalLot и CoffeeBag атомарно. Если выбран существующий личный лот, создаётся только новая пачка. При похожем названии показывается предложение использовать существующий лот; автоматического слияния нет.

### US-02. Оставить оценку

1. С карточки активной пачки открыть форму оценки.
2. Указать общую оценку 1–5.
3. При желании раскрыть шесть шкал и параметры приготовления.
4. Добавить текстовый комментарий и ответ «Купил бы ещё?».
5. Сохранить; запись сразу появляется в истории пачки, сводка обновляется.

Повторное нажатие сохранения/сетевой retry не создаёт дубль. Отправка формы не завершает пачку и не списывает зерно. Можно добавить оценку задним числом и к законченной пачке.

### US-03. Завершить или снова открыть пачку

Кнопка «Пачка закончилась» меняет статус и предлагает необязательное итоговое впечатление: 1–5, повторная покупка, комментарий. Пропуск разрешён. Можно отменить завершение и снова сделать пачку активной. Итоговая оценка хранится отдельно от оценок чашек.

### US-04. Повторить покупку

На странице личного лота нажать «Купил ещё пачку». Создаётся новая пачка с массой 250 г по умолчанию. Предыдущая пачка и её история остаются неизменными. Фото прошлой пачки может показываться как фото лота с подписью; оно не выдаётся за фотографию новой покупки.

### US-05. Связать с каталогом

В карточке личного лота выбрать «Связать с каталогом». Поиск по названию/обжарщику и вставка ссылки доступны. Показать кандидатов и их свойства, попросить выбрать точный товар. Связь обратима. Новая связь пересчитывает рекомендации, но не перезаписывает введённое пользователем название, фото, оценки и комментарии.

### US-06. Получить рекомендацию

Открыть «Что попробовать», выбрать бюджет и режим «Новое», «Повторить» или «Все». Получить до 10 карточек, причины рекомендации, уровень уверенности, доступную фасовку и ссылку на источник. Действия: «В избранное», «Скрыть», «Уже купил». Последнее создаёт пачку после подтверждения названия/массы и сохраняет связь с каталогом.

### US-07. Пользоваться дневником при сбое источника

Если сайт магазина недоступен, создание пачек и оценок продолжает работать. Рекомендации используют последний успешный снимок с отметкой времени; при сильном устаревании уходят из основной выдачи по правилам раздела 12.

## 7. Формы, шкалы и валидация

### 7.1. Лот и пачка

| Поле | Обязательность и правила |
|---|---|
| Название | Обязательно, trim, 1–200 символов |
| Обжарщик | Необязательно, до 120 символов; Фолк/Tasty из справочника или ручной ввод |
| Масса пачки | Обязательно технически; default 250 г, 1–5000 г |
| Дата покупки | Необязательно, не позже сегодняшней локальной даты |
| Дата обжарки | Необязательно, не позже сегодня; необычная последовательность дат — предупреждение, не потеря данных |
| Цена покупки | Необязательно, decimal >=0; отдельно от каталожной цены |
| Фото | Необязательно, 0–5 фотографий на пачку, одно основное |
| Заметка о пачке | Необязательно, до 5000 символов |
| Ссылка источника | Необязательно; привязка только к двум поддерживаемым доменам |

### 7.2. Оценка приготовления

Все числовые шкалы содержат только целые 1, 2, 3, 4, 5. На экране должны быть подписаны все значения или доступны пояснения. Не использовать предвыбранную середину шкалы.

| Поле | Значения/пояснение |
|---|---|
| Общая оценка — обязательно | 1: совсем не понравилось; 2: скорее не понравилось; 3: нормально; 4: понравилось; 5: очень понравилось |
| Кислотность | 1: не ощущаю; 2: слабая; 3: средняя; 4: сильная; 5: очень сильная |
| Горечь | Те же пять градаций интенсивности |
| Сладость | 1: не ощущаю → 5: очень выраженная; без добавленного сахара |
| Терпкость/сухость | 1: не сушит → 5: сильно сушит/стягивает рот; не смешивать с горечью |
| Плотность | 1: водянистый; 2: лёгкий; 3: средний; 4: плотный; 5: очень плотный/обволакивающий |
| Аромат | 1: почти не ощущаю → 5: очень интенсивный; это сила, не приятность аромата |
| Купил бы ещё | YES / MAYBE / NO / null |
| Комментарий | Необязательный, до 5000 символов, plain text |
| Дата/время | Default сейчас, можно изменить; будущее не допускается |
| Не уверен в приготовлении | Boolean, default false; не превращает оценку в недействительную |

Для каждого сенсорного поля хранить answer_status: UNANSWERED, UNKNOWN или RATED. Число допустимо только для RATED. UNKNOWN означает явное «Не могу оценить»; UNANSWERED — вопрос пропущен. Оба не участвуют в средних и не заменяются нулём/тройкой.

### 7.3. Необязательные пожелания к чашке

Мультивыбор: LESS_ACIDITY, MORE_ACIDITY, LESS_BITTERNESS, MORE_SWEETNESS, LESS_DRYNESS, MORE_BODY, LESS_BODY, MORE_AROMA, NOTHING_TO_CHANGE. Противоположные варианты одной шкалы несовместимы; NOTHING_TO_CHANGE исключает остальные. Пожелания сохраняются и показываются в истории; в V1 используются для объяснений, а не для неявного изменения оценок.

### 7.4. Параметры приготовления

- Профиль оборудования: default «Race M1 + Kitfort КТ-7570», можно создать другой.
- Метод: AUTO_POUR_OVER, POUR_OVER, DRIP, IMMERSION, ESPRESSO, OTHER. Начальный AUTO_POUR_OVER.
- Помол: общее число щелчков >=0 либо произвольная текстовая настройка для другой кофемолки. У Race M1 подпись «Общее число щелчков от нуля, включая полные обороты». Не задавать рекомендованный помол автоматически.
- Доза кофе: необязательные 0.1–200 г; вода на входе: 1–5000 г; температура: 1–100 °C; время приготовления: 1–3600 секунд.
- Вода: необязательная строка до 200 символов; тип фильтра/заметка о рецепте — до 500 символов.
- Наличие молока/сахара: NONE / MILK / SUGAR / BOTH / UNKNOWN. Default NONE в исходном профиле; всегда видно и редактируется.

Профиль хранит оборудование и обычный рецепт. При создании оценки подставляются его параметры и последнее сохранённое значение помола для этой пачки; сенсорные оценки и общая оценка никогда не копируются. Значения рецепта сохраняются в Tasting как снимок: изменение профиля не меняет историю. Пустой рецепт допустим.

Короткая форма содержит общую оценку, повторную покупку и комментарий. Подробная добавляет все шкалы и рецепт. Переключение не стирает введённое. Последний выбранный режим запоминается.

## 8. Жизненный цикл и исторические данные

CoffeeBag.status: STOCK → ACTIVE → FINISHED. Разрешены обратные переходы, включая FINISHED → ACTIVE. При первом открытии выставляется opened_at; при завершении — finished_at. Повторное открытие очищает текущий finished_at, но переход сохраняется в BagStatusEvent. opened_at не перезаписывается без явного редактирования.

Статус «Удалена» реализуется через deleted_at, отдельно от бизнес-статусов. Удаление пачки/лота/оценки — мягкое, с возможностью восстановления из «Удалённые». Каскадное скрытие оценок при удалении пачки не должно мешать восстановлению. В V1 автоматического окончательного удаления нет; административная очистка описана отдельно в README. Удалённые данные исключены из рейтинга и рекомендаций.

Сводки:

- оценка пачки: среднее общей оценки её действующих приготовлений; показывать n;
- сенсорные средние: по каждой шкале свой n, только RATED;
- итоговое впечатление о пачке показывается отдельно, не подменяет оценки чашек;
- личный рейтинг лота: среднее оценок его пачек, каждая пачка имеет равный вес; пачки без оценок исключаются;
- если итоговая оценка указана, в персонализации она имеет приоритет для этой пачки; в интерфейсе источник такого значения подписан;
- новый лот без оценок — «Ещё нет оценок», не 0/5;
- история оценок сортируется по tasted_at; изменения сохраняют created_at, updated_at и version.

## 9. Экраны и интерфейс

Навигация телефона: «Сейчас», «История», «Что попробовать», «Настройки». На больших экранах допустима боковая навигация. Каталог доступен из рекомендаций отдельной вкладкой/ссылкой.

### 9.1. Сейчас

Карточки активных пачек: фото/заглушка, название, обжарщик, дата открытия, количество выпитых чашек и оценок, средняя оценка, последняя оценка. Основное быстрое действие — «Выпил чашку», отдельное — «Оценить». Вторичные — открыть карточку, закончить пачку. Отдельный сворачиваемый блок «В запасе». Добавление кофе доступно всегда. Над карточками — итог за сегодня и общая кнопка «Выпил другой кофе».

### 9.2. Карточка лота/пачки

Общие сведения, фото с просмотром, статус и даты, ссылка на каталог, сводка шкал с количеством измерений, хронология чашек, список других пачек того же лота. У каждой чашки — рецепт, оценка, шкалы, комментарий, редактирование/удаление. Кнопки «Новая пачка» и «Оценить» не должны путаться.

### 9.3. История

Представления «Лоты», «Пачки», «Оценки», «Выпито». Поиск по названию/обжарщику, фильтры статуса, источника, общей оценки, периода. Сортировки: последнее использование, оценка, название. По умолчанию последние использованные. Пагинация/cursor; не загружать всю историю на телефон. Все фильтры имеют сброс. Во вкладке «Выпито» доступны суммарные чашки/мл и фильтры известных/неизвестных лотов.

### 9.4. Рекомендации

Карточка содержит: название, обжарщик, обложку источника при наличии, фасовку/цену, почему предложено, уверенность, «новый/уже пробовал», время проверки наличия, ссылку на оригинал. Не выдавать внутренний score за процент вероятности понравиться.

Разделы: «Близко к вашим удачным покупкам», «Для знакомства», «Можно повторить». В холодном старте первый раздел заменяется текстом «Пока мало ваших оценок» и общим каталогом/исследовательской подборкой. Доступны wishlist и список скрытых с отменой скрытия.

### 9.5. Настройки

Профиль оборудования, обычный рецепт, часовой пояс, фильтры рекомендаций: цена за 250 г, обжарщики, наличие кофеина (ANY/REGULAR/DECAF/LOW_CAF), тип обжарки (FILTER/OMNI по умолчанию; UNKNOWN по отдельному переключателю). Значение бюджета изначально не задано. Информация о последнем импорте, ручное обновление с ограничением частоты, экспорт собственных данных, смена пароля.

### 9.6. Общие требования UI

- Работоспособность при ширине 360, 390, 768 и 1440 px без горизонтальной прокрутки основного интерфейса.
- Touch targets не менее 44×44 CSS px для основных элементов; формы доступны без hover.
- Сенсорные шкалы — подписанные кнопки/radio, доступные с клавиатуры и screen reader. Цвет не единственный носитель смысла.
- Фото выбирается через стандартный input file; на мобильном предложить съёмку камерой. Галерея остаётся доступна.
- Все формы имеют состояния loading/saving/error/success; ошибка сети не очищает введённые данные.
- При уходе с несохранённой формы предупредить. Обязательного сохранения черновиков между перезапусками браузера нет.
- Не выводить профессиональные термины без короткой подсказки. Не показывать внутренние ML/ETL-поля обычному пользователю.
- Не прятать предупреждение об устаревшем каталоге в технических логах.

## 11. Учёт выпитого кофе — обязательная часть V1

### 11.1. Независимость от дегустации

ConsumptionEvent — источник истины для количества выпитого. Tasting — источник истины для вкусовых оценок. Количество оценок нельзя использовать как количество чашек. Одна чашка может не иметь оценки; оценка за прошлое приготовление не должна молча увеличивать счётчик.

- Нажатие «Выпил чашку» на карточке пачки создаёт один ConsumptionEvent с её bag_id.
- Нажатие «Выпил другой кофе» открывает небольшую форму: «Выбрать пачку» либо «Не знаю лот / другой кофе», профиль, объём, время. В режиме неизвестного кофе bag_id=null, название/комментарий необязательны.
- Неизвестный кофе учитывается даже при отсутствии личных лотов и активных пачек.
- Можно выбрать любую неудалённую пачку, включая законченную для записи задним числом. Статус пачки не меняется автоматически.
- Один event означает одну выпитую порцию/чашку. Объём может быть изменён, в том числе если выпита только часть. Это не число приготовленных кофейников.
- Объём — количество выпитого напитка, а не вода, залитая в кофеварку. Поле water_g рецепта нельзя использовать как cup_volume_ml.
- Количество чашек и объём не интерпретируются как кофеин, доза зерна или медицинская оценка. Расчёт кофеина вне V1.

### 11.2. Профиль и объём

В BrewProfile добавить default_cup_volume_ml: целое 10–2000 мл. Начальное техническое значение — 250 мл, с явным предложением настроить при первом использовании; это не утверждение о реальной чашке пользователя. Допустить дополнительный профиль «Вне дома», где кофемолка и кофеварка не указаны. Исходный домашний профиль связан с Race M1 и КТ-7570.

При записи выпитого объём берётся из выбранного профиля и сохраняется в event как снимок. Для быстрого действия на карточке используется default_brew_profile_id владельца; рядом доступна смена профиля перед действием. В общей форме «другой кофе» профиль можно выбрать или убрать. Изменение профиля с 250 на 200 мл не пересчитывает старые события. Разовая правка объёма не меняет профиль. Если профиль не выбран, пользователь вводит объём либо явно принимает показанное значение 250 мл; неизвестный объём не превращать в ноль. Архивирование профиля по умолчанию требует сначала выбрать другой; старые снимки остаются.

### 11.3. Быстрый сценарий и защита от дублей

На домашней карточке кнопка показывает «Выпил чашку · 250 мл». После успешного нажатия обновляются счётчики и появляется сообщение с действиями «Отменить» и «Оценить». Повторное намеренное нажатие после завершения запроса создаёт ещё одну чашку. Пока запрос выполняется, кнопка блокируется.

Каждое намеренное действие генерирует client_event_id UUID. Повтор HTTP-запроса с тем же ID возвращает тот же event, не добавляет чашку. Идентификатор нельзя переиспользовать для другой чашки. Сетевой timeout показывать как неопределённый результат с безопасным retry того же ID.

«Оценить» из сообщения/истории открывает форму с consumption_event_id. Сохранение оценки создаёт Tasting и связывает его с существующим event атомарно; новый ConsumptionEvent не создаётся. Если анкету закрыли, выпитая чашка остаётся учтённой. Для event неизвестного кофе предложение оценить недоступно до явного выбора/создания лота и пачки: оценка неизвестного кофе вне V1, его учёт обязателен.

Обычная форма оценки имеет отдельный непредвыбранный пункт «Также учесть выпитую чашку». Если он выбран, backend атомарно создаёт Tasting и ConsumptionEvent. Если форма уже открыта из event, вместо пункта показано «Чашка уже учтена». Редактирование оценки не создаёт чашек. Несовпадение bag_id у связанной оценки и event запрещено.

### 11.4. Редактирование, удаление, история

В event можно исправить время, объём, профиль, текстовую пометку и принадлежность пачке. Если есть связанная оценка, смена пачки требует согласованного изменения обеих записей в одной транзакции либо предварительного отвязывания. Нельзя оставлять противоречивую пару.

Удаление оценки не удаляет выпитую чашку; связь снимается. Удаление event не удаляет оценку; связь снимается. При восстановлении удалённой записи связь автоматически не восстанавливать, чтобы не перезаписать новую привязку; пользователь может связать её заново. Удаление пачки (в том числе через удаление личного лота) скрывает её из дневника, но не удаляет фактически выпитые чашки: у event сохраняется ссылка/снимок с подписью «Удалённая пачка», статистика остаётся прежней. Это исключение из каскадного скрытия раздела 8. Восстановление возвращает отображение пачки. Можно отдельно удалить любой event из статистики и восстановить его.

История показывает дату/время, название лота либо «Неизвестный кофе», объём, профиль, наличие оценки. Не создавать одну общую PersonalLot «Неизвестный кофе»: отдельные неизвестные чашки нельзя считать одним вкусом.

### 11.5. Статистика

- На главной: «Сегодня: N чашек · V мл».
- На странице статистики: день, текущая календарная неделя с понедельника, текущий календарный месяц, произвольный диапазон дат.
- Count = число неудалённых events; volume = сумма их volume_ml. Известные и неизвестные входят одинаково.
- Фильтры: профиль, пачка/лот, известный/неизвестный кофе. Итоги пересчитываются по фильтрам.
- Дни группируются в часовом поясе профиля пользователя; интервал дат задаётся [начало первого дня, начало дня после последнего). 23:59 и 00:01 попадают в соответствующие локальные дни.
- Для произвольного периода вернуть дневные точки, включая нули. Достаточны таблица/небольшая столбчатая диаграмма с текстовыми итогами.
- Изменение и удаление событий обновляют итоги сразу. Первичные события важнее кэша; агрегаты восстанавливаемы.
- Рекомендательная модель не трактует частоту питья как лайк: покупка пачки и допивание кофе не доказывают предпочтение. В V1 ConsumptionEvent не влияет на taste score.

## 12. Получение каталога и отзывов

### 12.1. Источники и обязательное исследование до реализации адаптеров

Источники V1: https://folk.shop/ и https://shop.tastycoffee.ru/coffee/filter. Поддержать зерновой кофе FILTER и OMNI; кофе для эспрессо хранить при простом получении, но не показывать в фильтровой подборке по умолчанию. Дрипы, капсулы, молоко, мерч и аксессуары исключить из кандидатов.

Наблюдения на дату подготовки ТЗ:

- Folk публикует каталог и дескрипторы; текстовое получение страницы может возвращать только оболочку. Наличие доступных пользовательских отзывов у Folk не подтверждено.
- Tasty публикует карточки с описанием, характеристиками, комментариями и рецептами. Это не означает существование стабильного публичного API.
- На постоянной карточке товар может сохранять название при изменении входящих лотов. Источник сам об этом сообщает для Бразилии Игуасу.

Эти наблюдения не являются готовым контрактом интеграции. Первый этап агента: проверить фактический HTML, публичные JSON-ответы/данные страницы, пагинацию, варианты веса, доступность комментариев и правила автоматического доступа. Описать findings в docs/source-adapters.md, приложить небольшие обезличенные fixtures и даты проверки. Не выдумывать API, external_id, CSS-селекторы или отзывы.

Приоритет получения: документированный разрешённый API/feed → публичные данные страницы → HTML → рендеринг публичной страницы через Playwright. Не использовать приватные аккаунты, обход CAPTCHA/блокировок. Если источник запрещает или технически блокирует получение, пометить BLOCKED, сохранить диагностику и реализовать контролируемый импорт нормализованного JSON. Такой fallback сохраняет работоспособность, но не считается выполненной живой интеграцией; блокер явно включить в отчёт приёмки.

### 12.2. Контракт адаптера

Одинаковый интерфейс для источников: listProducts(cursor), fetchProduct(externalId/url), fetchReviews(product,cursor), capabilities(), health(). Каждый метод возвращает данные, source_url, fetched_at, parser_version и structured warnings.

Минимум товарных данных: source, external_id или стабильный canonical_url, название, тип товара, URL, available/unknown, roast_profile/unknown. Дополнительно: происхождение, обработка, разновидность, урожай, описание, дескрипторы, шкалы производителя, варианты фасовки/цен, изображение.

Сохранять null для отсутствующих данных; не выводить обработку/урожай/плотность из страны или названия. «От 900 ₽» без веса не превращать в цену за 250 г. Хранить сырое значение и отмечать, что нормализованная цена неизвестна.

### 12.3. Синхронизация

Расписание: один запуск каждые 24 часа, плюс ручное обновление не чаще раза в 15 минут на источник. Тайминги конфигурируемы. Личные операции не ждут импорта.

- Одна активная задача на источник; блокировка в БД с heartbeat/timeout, защищает от параллельных запусков после рестарта.
- Начальный лимит: 1 запрос/секунду на домен, concurrency=1; соблюдать более строгие лимиты источника.
- HTTP timeout 20 секунд, максимум 3 попытки для сетевых/временных 5xx с backoff+jitter. Для 429 учитывать Retry-After, не долбить сайт. 401/403/CAPTCHA — BLOCKED без бесконечных retry.
- Полная пагинация каталога; товары коммитятся идемпотентно. Предыдущие успешные ревизии не удалять.
- Отзывы: до 100 последних содержательных записей на продукт за начальную загрузку, затем инкрементально, с конфигурируемым лимитом. Показывать fetched_count и признак неполноты; не писать «все отзывы», если скачана часть.
- Ключ отзыва: стабильный source_review_id, иначе hash(product + source author key + date + normalized text). Один отзыв не учитывается несколько раз после повторного импорта/редактирования.
- Ответ обжарщика, рецепт и отзыв покупателя — разные author_role/record_type, не три независимых голоса.
- При изменении разметки/нулевом результате после непустого успешного импорта считать запуск подозрительным, не помечать весь каталог распроданным.
- Только два подряд успешно завершённых полных прохода, в которых продукт отсутствует, позволяют считать его недоступным. Явная карточка out_of_stock применяется сразу. Ошибка загрузки не равна отсутствию товара.

CatalogSource.status: NEVER_SYNCED / OK / PARTIAL / FAILED / BLOCKED. Reviews capability/status хранить отдельно: AVAILABLE / NONE_CONFIRMED / UNKNOWN / BLOCKED / FAILED. Пустая непарсенная страница не подтверждает отсутствие отзывов. Дата последней попытки и последнего успешного обновления различаются.

### 12.4. Свежесть и работа без интернета

До 48 часов после успешной проверки — свежие данные. 48 часов–7 суток — показывать «Наличие и цена требуют проверки», использовать ниже свежих кандидатов. Старше 7 суток или без успешной проверки — исключить из основной выдачи доступных покупок, но оставить в каталоге/истории с пометкой. Пороговые значения конфигурируемы.

Отсутствие сети не блокирует дневник, статистику, фото и чтение последнего снимка. На пустой БД без сети показывать «Каталог ещё не загружен», а не демонстрационные лоты под видом актуальных.

### 12.5. Разбор описаний и отзывов

Нормализатор V1 создаёт версионируемый FeatureDocument с provenance. Базовая реализация без LLM:

1. Отдельно читает структурированные поля производителя.
2. Нормализует дескрипторы по контролируемому словарю групп: CHOCOLATE, NUTTY, CARAMEL, FRUITY, BERRY, CITRUS, FLORAL, TEA, FERMENTED, SPICY, EARTHY. Сохраняет исходные слова.
3. Из текста извлекает только явно выраженные категории интенсивности LOW/MEDIUM/HIGH и положительное/отрицательное отношение автора к конкретному признаку; неизвестное остаётся неизвестным.
4. Словари, отрицания и правила привязки к признаку проверяются fixtures. «Не кислый», «не сказал бы, что кислый», «не слишком кислый», «хотелось бы слаще» — разные случаи. Неуверенные конструкции пропускать; пожелание «слаще» не равно LOW sweetness.
5. «Смородина» даёт BERRY, но сама по себе не даёт HIGH acidity. «Тёмный шоколад» не даёт HIGH bitterness. «Насыщенный аромат» не даёт высокую плотность.
6. Общая звезда отзыва не преобразуется в интенсивность вкуса. Отзывы о доставке/упаковке без вкусовой информации не влияют на sensory features.

LLM-адаптер можно реализовать как необязательное улучшение за feature flag, но это не условие MVP. Если реализован: JSON Schema, temperature/модель в конфиге, ограничения размера, кэш по content hash и extractor_version, валидация evidence_span на наличие в исходном тексте, лимит стоимости и отказ в пользу базового парсера. Контент страницы считается недоверенными данными, не инструкцией. Личные комментарии/фото внешней модели по умолчанию не отправляются.

Численные шкалы производителя хранить с original_min/max/source. Их нельзя считать той же шкалой, что личная 1–5. Для вспомогательных feature buckets допустима явная техническая нормализация: u=(value-min)/(max-min); LOW при u<1/3, MEDIUM при 1/3<=u<=2/3, HIGH иначе. При неизвестных границах не нормализовать. Это относительный сигнал внутри шкалы источника, а не измерение вкуса.

По отзывам хранить распределение LOW/MEDIUM/HIGH и число независимых авторов. Для признака формировать representative bucket, если есть минимум 3 пригодных независимых наблюдения и не менее 2/3 согласны с одной категорией; иначе CONFLICTED/UNKNOWN. Отзывы от одного автора по одному продукту суммарно дают максимум один голос на признак; продолжения обсуждения объединяются. При неизвестном авторе использовать дедупликацию текста и понижать качество, не выдавать уникальность за подтверждённую.

Для пользовательского фильтр-профиля предпочтительны отзывы о чёрном кофе из POUR_OVER, AUTO_POUR_OVER и DRIP. Неизвестный метод помечается и получает меньшую надёжность. Молочные отзывы не используются для оценки чёрного кофе. Отзыв без уверенной связи с продуктом исключается. Для известной ревизии не переносить автоматически отзывы старой явно другой партии; неизвестная ревизия остаётся product-level с низкой надёжностью.

## 13. Рекомендательный алгоритм V1

### 13.1. Назначение и ограничения

Реализовать детерминированный объяснимый baseline, а не свободный ответ LLM «выбери кофе». Входы: пользовательские предпочтения, история, подтверждённые связи с каталогом, актуальные features/offer двух источников. Выход: упорядоченный набор продуктов, причины, уровень уверенности, неизменяемый снимок расчёта.

Шесть личных сенсорных шкал должны участвовать в персонализации при достаточных данных. Ниже задан начальный эвристический алгоритм; веса — инженерные гиперпараметры, вынесенные в конфиг. Он не обещает доказанной точности и должен сравниваться с базовыми вариантами после реальных покупок.

### 13.2. Отбор кандидатов

1. Товар — зерновой кофе из FOLK/TASTY, неудалённый и не скрытый пользователем.
2. Roast FILTER/OMNI по умолчанию; UNKNOWN только по переключателю; ESPRESSO при явном выборе пользователя.
3. Есть доступная покупаемая фасовка. UNKNOWN availability разрешён только в отдельном переключаемом блоке «Нужно проверить».
4. Проверены свежесть по разделу 12.4, настройки кофеина и обжарщика.
5. При установленном бюджете сравнивать RUB price_per_250g=price*250/weight_g. Неизвестная цена не проходит строгий бюджетный фильтр, но доступна в отдельном блоке. Показывать также реальную цену пачки и её вес: нормализованная цена не обещает продажу 250 г.
6. NEW исключает продукты, связанные с любой неудалённой пачкой владельца. REPEAT включает такие продукты с предыдущими оценками. ALL объединяет; активные пачки не предлагать повторно по умолчанию, есть переключатель «Включать то, что сейчас пью».
7. Сохранение/скрытие — действия выбора, не положительная/отрицательная дегустация.

Если фильтры оставили 0 вариантов, показать причины и предложить ослабить фильтр; не нарушать его молча.

### 13.3. Учебные опорные записи

Опорная запись — один подтверждённо связанный продукт/известная ревизия с личной оценкой. Для каждой пачки: y_b = final_rating, если есть, иначе среднее overall_rating чашек. Для сенсорного d: z_b,d = среднее RATED по чашкам этой пачки. Отдельно группировать совместимые способы приготовления; для исходного профиля использовать фильтр-методы без молока/сахара. Если способ неизвестен, опору можно использовать с коэффициентом 0.5; явно другой метод исключить из этой подборки.

Повторные пачки одной версии объединить равными весами в y_j и z_j,d; число чашек не увеличивает вес продукта. При неизвестной версии повторные покупки одного продукта дают одну опору с пометкой низкой уверенности. Опоры с preparation_uncertain не удаляются: для оценки конкретной чашки перед усреднением использовать вес 0.5 вместо 1. Итоговая оценка пачки не наследует эту неопределённость автоматически.

У PersonalLot без связи с каталогом остаётся весь дневник и сенсорный профиль, но нет внешних признаков для надёжного переноса на новый товар. Не пытаться приписать ему descriptors по названию. Показать ненавязчивое предложение «Связать с каталогом для более точных рекомендаций». Пользователь может вручную заполнить происхождение/обработку/дескрипторы как явно ручные features; тогда запись становится доступной опорой с соответствующим provenance.

Если подтверждённая ревизия отсутствует, допускается текущий product-level feature snapshot как приближение с коэффициентом надёжности 0.5 и подписью «Версия вашей пачки не подтверждена». Не представлять это как точное соответствие партии.

### 13.4. Сходство внешних признаков

Для кандидата c и опоры j рассчитать similarity s(c,j) только по известным обеим сторонам признакам. Веса:

| Признак | Вес | Сходство |
|---|---:|---|
| Группы дескрипторов | 3 | Jaccard множеств; два пустых множества считаются отсутствием данных |
| Обработка | 2 | Jaccard нормализованных кодов |
| Профиль обжарки | 2 | 1 при совпадении; 0.5 FILTER↔OMNI; 0 иначе |
| Страна | 1 | 1 при совпадении, 0 иначе; смеси — пересечение множеств |
| Регион/ферма | 1 | 1 при точном нормализованном совпадении, 0 иначе; отсутствующее пропустить |
| Разновидность | 0.5 | Jaccard |
| Внешние sensory buckets | 1.5 | Среднее по общим известным измерениям: 1 одинаковые, 0.5 соседние, 0 крайние |

Для sensory buckets сначала брать согласованные пользовательские отзывы при выполнении порога раздела 12.5, иначе явно опубликованную категорию производителя. CONFLICTED не заменять уверенным средним. Если хотя бы одна сторона использует шкалу производителя другого источника, вес sensory блока уменьшить вдвое; сохранять предупреждение о несопоставимых шкалах.

similarity = сумма(weight*similarity_dimension) / сумма доступных весов. coverage = сумма доступных исходных весов / 11.0. Числитель coverage использует вес 1.5 sensory, только если есть >=2 общих сенсорных измерения; частичный блок с 1 измерением даёт 0.75. В similarity для одного измерения также использовать вес 0.75. Не учитывать принадлежность одному обжарщику как бонус: иначе межобжарщиковые рекомендации подавляются.

Опора участвует, если coverage>=0.35 и similarity>=0.45. Коэффициент a_j = similarity² * coverage * reliability, где reliability=1 для подтверждённой версии/метода, 0.5 для каждого из двух признаков неопределённости версии/метода (при обоих 0.25). Взять до 5 опор с максимальным a_j; tie-break по UUID. Нет опор — персональный прогноз отсутствует.

### 13.5. Прогноз оценки и собственных ощущений

Для выбранных опор:

- prior — среднее y_j по всем доступным различным опорам пользователя; если их нет, технически 3, но не выводить как персональный прогноз.
- y_hat = (sum(a_j*y_j) + 0.5*prior) / (sum(a_j)+0.5).
- Для каждой личной сенсорной шкалы d: z_hat_d = sum(a_j*z_j,d)/sum(a_j) по опорам с известным z_j,d. Если меньше двух различных опор — значение не прогнозировать.
- Это прогноз того, как пользователь может оценить ощущения по аналогии с прошлым опытом. Не преобразовывать внешнюю HIGH acidity напрямую в личную 5/5.

Чтобы личные сенсорные оценки влияли на порядок, сформировать набор положительных опор P с y_j>=4. Для каждой p из P, где с прогнозом есть минимум 3 общие шкалы, рассчитать distance_p = mean(abs(z_hat_d-z_p,d)/4). taste_fit=1-min(distance_p). Использование ближайшего понравившегося профиля допускает несколько направлений вкуса и не усредняет их в один «идеальный кофе».

Если есть taste_fit: personal_score=0.8*((y_hat-1)/4)+0.2*taste_fit. Если taste_fit не определён, personal_score=(y_hat-1)/4, без наказания за незаполненные шкалы. Ограничить score диапазоном [0,1]. Противоположные оценки прошлых лотов влияют через y_j; не исключать их из обучения.

Для REPEAT при подтверждённой той же версии использовать прямую личную оценку соответствующей опоры; для новой/неизвестной партии — обычный прогноз с предупреждением. Не показывать прошлую оценку как гарантированную оценку текущей партии.

### 13.6. Холодный старт, уверенность, разнообразие

Нет опор: только каталог под фильтры и раздел «Для знакомства», без «Вам понравится». Исследовательский выбор детерминирован: отсортировать свежие подходящие товары по стабильному hash(owner_id, date, product_id), выбирать по одному из разных групп обработка+дескриптор, пока возможно, чередуя источники; максимум 2 из одной группы в первых 5, если альтернатив достаточно. Не выдавать случайный порядок за качество.

1–2 опоры: предварительный personal_score, уверенность только LOW. При 3+ опорах можно персонализировать. Уверенность — полнота доказательств, не вероятность:

- LOW: <3 подходящих опор, или mean coverage<0.5, или неопределённая версия/сильно противоречивые признаки.
- MEDIUM: >=3 подходящих опор, mean coverage>=0.5, свежий кандидат, без указанных критичных неопределённостей.
- HIGH: не применять в V1 до проверки качества на отложенных реальных дегустациях. Для повторной покупки можно отдельно писать «Вы уже оценили этот кофе», не обещая точность прогноза.

Основная выдача в ALL: до 5 близких новых товаров по personal_score, отдельно до 3 исследовательских, отдельно до 2 повторных (всего до 10). В NEW доступны до 7 близких и до 3 исследовательских; в REPEAT — до 10 повторных. При холодном старте — до 10 для знакомства. Товар не дублируется в разделах. При равенстве score: свежесть → наличие фасовки 250 г → меньшая нормализованная цена → product_id. Межобжарщиковое разнообразие применяется только между кандидатами, отличающимися по score не более чем на 0.05, чтобы не ломать явное предпочтение. Больше отзывов само по себе не повышает personal_score.

### 13.7. Объяснения, воспроизводимость, проверка пользы

Каждая персональная карточка должна ссылаться минимум на одну реальную опорную покупку и известные совпадающие признаки: «Похож по обработке и ягодным описаниям на X, который вы оценили на 4/5». Вторая строка — конкретная неопределённость. Не писать «люди с вашим вкусом», если поиск таких людей не реализован. Не писать «без горечи», если она просто не упомянута.

Объяснения генерируются шаблонами из Reasons DTO. Любое число отзывов вычисляется из реально полученных пригодных отзывов; признак частичной выборки виден. По клику «Почему» показать исходные ссылки, источник признака (обжарщик/покупатели/ваши оценки), опорные лоты и дату обновления.

Сохранять RecommendationRun до следующей дегустации: algorithm_version, входные ревизии, использованные опоры, score components, confidence, причины и сортировку. Пересчёт при изменении личных оценок, привязки, фильтров, catalog revision, удаления/восстановления. Записи ConsumptionEvent без оценки модель не меняют. Старые runs неизменяемы.

Сохранять параллельный baseline score по описанию производителя без review features. После оценки купленного рекомендованного товара сравнить прогнозы до покупки с фактом: абсолютная ошибка общей оценки и доля повторных покупок с final_rating>=4. Считать на уровне различных купленных продуктов/версий, не каждой чашки. Пока наблюдений мало, показывать в диагностике число случаев, не заявлять улучшение качества. Данные новой оценки не должны попадать в прогноз, с которым её сравнивают.

- Auth required для всех пользовательских endpoint, фото, экспорта и диагностики. Health endpoint без личных сведений может быть публичным.
- 201 для создания, 200 для идемпотентного повтора, 204 для успешного удаления; 400/422 валидация, 401 без сессии, 403 недостаточно прав, 404 отсутствует/не принадлежит владельцу, 409 конфликт версии/состояния, 413 превышение размера, 429 лимит.
- Ошибка JSON: code, message, fieldErrors, requestId. Не раскрывать stack trace, пароли, cookie и ответы источника целиком.
- PATCH принимает version/If-Match; конфликт редактирования в двух вкладках не затирает данные молча.
- Списки limit default 20, max 100; стабильная сортировка по timestamp+id. Фильтры и порядок документировать.
- Для POST пачек/оценок/потребления использовать Idempotency-Key или client_event_id. Хранить owner+key+request_hash+result; повтор с другим payload →409. Для consumption client_event_id уникален постоянно; прочие ключи хранить минимум 24 ч.
- Строки трактуются как текст. URL источника нормализуются сервером. Нельзя передавать произвольный URL в серверный скачиватель.
- DTO возвращает расчётные summaries, но клиент не может записать собственное среднее/рейтинг в БД.

## 15. Фотографии, доступ и надёжность

### 15.1. Хранение фото

Принимать JPEG/PNG/WebP, до 10 MiB на файл, максимум 5 фото на пачку. Проверять сигнатуру, декодирование и предельное число пикселей 40 мегапикселей. SVG и произвольные файлы не принимать. HEIC/HEIF в V1 не обязателен: понятное сообщение «Сохраните фото в JPEG/PNG»; не обещать поддержку без декодера и теста.

При обработке исправить EXIF orientation, удалить EXIF/GPS, сформировать нормализованное основное изображение (длинная сторона до 2560 px) и thumbnail до 480 px с сохранением пропорций. Если исходник больше, в V1 допускается хранить только нормализованную версию; в UI не называть её неизменённым оригиналом. Фото не отправляется на внешние сервисы.

Storage keys случайные, не пользовательские пути/названия. Volume переживает restart/recreate контейнера. Временная загрузка имеет owner и статус PENDING; при сохранении пачки привязывается транзакционно в БД. Непривязанные PENDING старше 24 ч очищаются. Сбой фото не приводит к исчезновению сохранённой пачки; UI предлагает повторить загрузку.

Файлы отдавать через авторизованный endpoint или защищённый reverse proxy, не через публичную папку. Ссылки на внешние картинки каталога не смешивать с личными фото. При недоступности внешней обложки использовать заглушку; при локальном кэшировании соблюдать allowlist источников и лимит загрузки.

### 15.2. Авторизация и безопасность

Один владелец создаётся bootstrap-командой или одноразовым onboarding при пустой БД; публичной регистрации нет. Пароль хранится современным адаптивным хэшем (например Argon2id через поддерживаемую библиотеку). Bootstrap secret не попадает в git и логи. Документировать сброс пароля локальной административной командой.

Для браузера same-origin cookie session: HttpOnly, Secure в HTTPS, SameSite=Lax, CSRF-защита для изменений, разумный срок жизни сессии и logout invalidation. Ограничение попыток входа. Если сессии в памяти, logout после restart допустим, потеря дневника — нет. Не хранить долгоживущий токен в localStorage.

Проверять owner на каждой личной операции, включая media ID. Защита от XSS: комментарии plain text, описания источника очищать, не рендерить сырой HTML. SSRF: запросы только к явно разрешённым источникам/их документированным CDN, проверять каждый redirect, запрещать localhost/private/link-local IP и нестандартные схемы. Парсеры имеют лимиты размера/времени. Конфиденциальные URL и cookie не логировать.

### 15.3. Резервное копирование и эксплуатация

README содержит команды: старт, миграции, bootstrap, логи, backup, restore в пустое окружение, обновление версии. Backup состоит из PostgreSQL dump, media volume и manifest версии приложения; обеспечить согласованность снимка (на время backup запретить изменения или описать согласованный механизм). Секреты копируются отдельно защищённым способом, не включаются в пользовательский export.

Export возвращает личные лоты, пачки, оценки, ConsumptionEvent, профили и фото с manifest. Внешние отзывы/полные каталоги в пользовательский export не обязательны; хранить ссылки и внешние ID для связей. Импорт export через UI вне V1, но restore из операционного backup обязателен.

Логи структурированные: requestId/importRunId, длительность, безопасные коды ошибок. Health: БД, файловое хранилище; stale источник не делает diary health DOWN. Отдельная диагностика состояния импорта/последней успешной синхронизации.

### 15.4. Производительность и объём

Тестовый ориентир: 1 пользователь, 500 личных лотов, 2000 пачек, 10 000 оценок, 20 000 событий выпитого, 2000 товаров каталога. На локальном стенде 2 vCPU/4 GB RAM, без времени внешней сети: обычные API p95 <=500 мс; чтение кэшированных рекомендаций <=1 с; полный пересчёт <=5 с. Измерить и указать фактический стенд. Не обещать эти числа без замера.

Первый экран показывает текст/карточки без ожидания всех фотографий. Фото lazy-load, thumbnail для списков. Импорт и обработка больших наборов не блокируют HTTP-потоки дневника. Отсутствие внешнего AI-сервиса никак не блокирует основную работу.

## 16. Критерии приёмки

| ID | Проверяемое поведение |
